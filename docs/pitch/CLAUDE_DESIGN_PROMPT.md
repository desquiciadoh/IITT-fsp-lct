## 0. Роль и задача

Ты ведущий презентационный дизайнер и продуктовый стратег. Собери финальную презентацию для питч-сессии жюри трека Федерации спортивного программирования (ФСП) на хакатоне «Лидеры цифровой трансформации 2026». Цель: первое место. Продукт: **FSP Draft**, платформа обратного IT-рекрутинга с верифицированным профилем достижений участника ФСП.

Формат сдачи: **.pptx (16:9, 13.333×7.5 in)**, редактируемый, плюс экспорт в PDF. Язык слайдов: русский. Чтение жюри: это люди из ФСП и ИТ-индустрии, они видели десятки хакатонных питчей. Выигрывает тот, кто показывает **измеримые доказательства и честность**, а не лозунги.

Приложены: шаблон организаторов (.pptx) и ТЗ (.pdf). **Шаблон обязателен к использованию**: его шрифт, цвета, структура обязательных слайдов (ниже). Не выдумывай свой стиль поверх.

## 4. Нарратив питча (6–7 минут) и сквозная метафора

Метафора: **спортивный драфт**. Клубы не читают резюме игроков, они выбирают по проверенной статистике. ФСП это спортивная федерация, образ считывается мгновенно. Словарь: Лига = категория (специализация × грейд), Карточка игрока = профиль, Квалификация = тест, Скаутинг = пул кандидатов, Драфт-оффер = приглашение, трансферное окно = кулдаун смены грейда.

Дуга: Крючок → Боль → Решение в одну фразу → Как это работает (демо-путь) → **Почему механика новая** → **Почему тесту можно верить** → Доказательства → Готовность к реальному ФСП → Бизнес и развитие → Призыв.

Крючок для титула/2-го слайда (можно улучшить): *«Клубы не читают резюме игроков. Они выбирают по проверенной статистике. Почему IT-найм до сих пор идёт по самописным резюме?»*

## 5. Самые сильные стороны проекта (только проверенные факты; формулируй ими, ничего не добавляй от себя)

### 5.1 Новая механика подбора (35 %): «обратный найм»
- Работодатель сам просматривает **ранжированные Лиги** (Backend / Frontend / ML & Data × Intern / Junior / Middle / Senior = 12 лиг) и шлёт адресный **Драфт-оффер**. Кандидату не нужно откликаться вслепую.
- **Salary-first**: зарплатная вилка «от–до» в рублях + gross/net обязательна и в вакансии, и в оффере. Проверяется в трёх местах: CHECK-ограничения в БД, валидаторы DRF, тесты. Оффер без вилки физически не сохранить.
- **Нулевая утечка контактов**: контакты лежат в отдельной таблице, зашифрованы AES-256-GCM at rest, работодатель получает их только через `ContactGrant`, который создаётся автоматически при переходе оффера в `accepted`. Любая попытка прочитать раньше → 403 + запись в `AuditLog`. Кандидат может отозвать доступ. Покрыто тестами.
- **Машина состояний оффера**: `sent → viewed → accepted / declined / withdrawn`, автоистечение через 14 дней, оптимистичные блокировки (`version`), конкурентные accept/withdraw → побеждает одно действие, второе получает 409. Обе стороны видят статусы **в реальном времени (SSE)**.
- **Объяснимое ранжирование**: счёт 0–100 = взвешенная сумма шести признаков (SkillFit 35, Strength 20, GradeFit 15, SalaryFit 15, SemanticFit 10, Freshness 5). Для каждого кандидата показываются **чипы-причины** с источником достоверности: `✓ проверено тестом`, `🏆 подтверждено ФСП`, `заявлено кандидатом` (пунктирная рамка у заявленного, сплошная у проверенного). **Сумма вкладов = итоговому баллу**, это инвариант, проверяемый тестами. Показываются `gaps` (чего не хватает из must-have).
- **Контрфактические подсказки**: «убери Kubernetes из обязательных → +23 кандидата». Работодатель понимает, что менять, если пул пуст.
- Шорт-лист **не теряется** при смене фильтров и весов; пресеты Balanced / Skills-first / Budget-first и слайдеры пересчитывают выдачу сразу.
- **JD → структура**: работодатель вставляет текст вакансии, система извлекает стек (must/nice), грейд, вилку, формат и сама строит блюпринт теста.
- **Защита от спама и недобросовестных работодателей** (бонус по ТЗ, реализовано, не концепция): кредиты на приглашения в неделю, проверка ИНН, лимиты частоты, проверка аномальных зарплат, **приватный зарплатный порог кандидата** («оффер ниже порога» видит только отправитель, как да/нет, без раскрытия суммы), Need Health: структурные причины отказов («чаще всего отказываются из-за зарплаты»), прогноз вероятности принятия (низкая/средняя/высокая).
- **Приватность кандидата**: слепой режим, чёрный список компаний (скрыть профиль от текущего работодателя), раздельные согласия 152-ФЗ с версиями.

### 5.2 Тестирование (25 %): «тест, который нельзя слить»
- Проблема из ТЗ: единый набор заданий утекает, задания от нейросети несопоставимы по сложности. Наше решение: **параметрические семейства заданий** (`ItemFamily`). Каждое задание это генератор, а не вопрос: код, данные, имена и числа случайны от seed, **ответ вычисляет независимый детерминированный оракул** (Python, in-memory SQLite, симулятор event loop, настоящий Node.js для JS-семейств). Утечка одного экземпляра ничего не даёт, следующий кандидат получит другой.
- **LLM никогда не выставляет оценку и не решает грейд**. Не «осторожно», а архитектурно: тест на инвариант в CI. Это ответ на вопрос «почему не генерировать вопросы нейросетью»: цена ошибки и несопоставимость, поэтому LLM только готовит черновики офлайн, а в тесте работают верифицированные генераторы.
- **Адаптивный тест (CAT) на шкале IRT**: 3PL-модель, оценка EAP по 61-точечной сетке с нейтральным N(0,1) априором, выбор задания по максимуму информации Фишера **под квоты блюпринта** (разные темы покрыты у всех, значит грейды сопоставимы), randomesque top-5 для контроля экспозиции, правила остановки (SE ≤ 0.30 или доверительный интервал за границей грейда, 10–20 заданий). Рейтинг = 1000 + 200θ **с доверительным интервалом** («1085 ± 60»).
- **Нейтральный априор**: заявка на высокий грейд не завышает оценку. Первое задание целится в заявленную границу, но оценка считается без учёта заявки.
- **Грейд не понижается принудительно** (требование ТЗ): не подтвердил заявленный, остаётся в базе со статусом `unconfirmed` (видим, ранжируется ×0.75), бесплатный **fallback** на ступень ниже, если P(θ ≥ граница) ≥ 0.8; **promotion** вверх, если P ≥ 0.9; кулдаун смены грейда 30 дней, на сервере (не только в UI).
- **Доказательство устойчивости к утечкам**: 63 параметрических семейства; harness генерирует по 1 000 экземпляров на семейство и проверяет: ключ совпадает с оракулом, ровно один верный ответ, коллизии ≤ 0.1 %, энтропия ответов > 1 бита, **нельзя угадать по одним вариантам ответа** (тест-стратегии «самый длинный/короткий/самый частый вариант» и т. д. не лучше случайного). Намеренно сломанные семейства harness отклоняет (15 негативных тестов). Сгенерированные ключи **не покидают сервер**: ни в сериализаторе, ни в логах, ни в ошибках.
- **Монитор утечек и дрейфа** в проде: сравнение наблюдаемой и ожидаемой доли верных ответов по диапазонам θ, FDR-контроль, автоматическая перекалибровка параметров семейства, выведение слабых семейств (так мы сами убрали 5 «классификационных» семейств, которые при 20 утёкших экземплярах повторялись с вероятностью ≥ 0.5).
- **Test Twins**: по вакансии строятся два теста-близнеца (те же семейства в каждом слоте, разные seed, идентичные a/b/c и информационные кривые). Наглядно показывает «разные задания, одинаковая сложность». Реализован в интерфейсе (раздел Test Twins на странице `/lab`, ключи ответов не показываются): хороший скриншот для слайда.
- **Как тест выдаётся сейчас (честная формулировка для слайдов и Q&A):** адаптивный движок CAT/IRT реализован и провалидирован симуляцией (§5.3). В живых сессиях платформы банк из 63 семейств покрывает все три специализации (Backend, Frontend, ML & Data), **Полный режим выдаёт 12 заданий, Экспресс 6**, семейства выбираются детерминированно (HMAC от секрета и id сессии) с ротацией по темам и порядком по возрастанию сложности. Не утверждай на слайде, что в живой сессии длина теста подбирается адаптивно по SE, если это не подтверждено; формулируй: «адаптивное ядро готово и откалибровано в симуляции, в демо — 12/6 заданий».
- Честная оговорка: тест это входной квалификатор без прокторинга; «Verified+» с прокторингом в roadmap. Не утверждай, что использование ChatGPT во время теста полностью исключено.

### 5.3 Валидация (часть критерия 2 и «честность»)

Синтетический мир: 1 500 кандидатов со скрытым латентным θ, 12 вымышленных компаний, 60 вакансий; симулируется 10 000 прохождений через **реальный продакшн-движок** с искажёнными параметрами заданий (чтобы движок не оценивался по своим же предположениям); оракул релевантности читает только скрытую «правду»; веса не подгонялись под оценочный набор.

**Как подать честно (это сильная позиция, не слабость):**
- Критерий 2 прямо оценивает «качество процедуры валидации и приведённых результатов». Наша позиция: *мы опубликовали 10 из 15 целей как промахи с причинами, потому что подгонка под оценочный набор убила бы доверие*. Покажи слайд «Что сработало / Что мы честно недотянули / Чем закрываем» (промахи: разрешающая способность банка заданий a≈1.0–1.4 и потолок 20 заданий; малый банк → высокая экспозиция; keyword-baseline выигрывает у нашего скорера на синтетическом оракуле, потому что в синтетическом мире заявленные навыки почти истинны, а оракул не учитывает зарплату, свежесть и силу; закрыто ML-13: утечные концепт-семейства выведены, параметрическая утечка = 0.00).
- Главный «выигрышный» график: **атака утечкой** (столбцы: статичный банк vs параметрический) и **информационная кривая теста**. Матрица ошибок 4×4 показывает, что ошибки почти всегда в соседний грейд (99.2 %).
- Не рисуй «наш скорер лучше keyword», этого нет в данных. Лифт честно сформулирован так: проверенное тестом/ФСП знание даёт то, чего нет у ключевых слов, а именно **объяснимость, защиту от завышенных резюме и контроль мошенничества**; на настоящих данных пилота сравнение будет пересчитано.
- В докладе: пилот на реальных людях и разметка экспертов (κ на 300 парах, Спирмен оракул–эксперт) **подготовлены как pipeline, данных пока нет** (`status: no_data`). Это пункт roadmap, не заявляй результат.

### 5.4 Интеграция с ФСП (кейс «нет истории ФСП» обязателен по ТЗ)
- **Keycloak-совместимый OIDC** (Authorization Code + PKCE, BFF: токены не попадают в браузер). Свой `fsp-id-mock` на путях `/realms/fsp/...`, discovery, JWKS. Переход на настоящий Keycloak = **три переменные окружения** (`OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`); realm-экспорт с маппером `fsp_participant_id` лежит в репозитории. Регистрация по email с подтверждением работает параллельно.
- **Предложенный контракт реестра ФСП** (`GET /participants/{id}/achievements`): спортивный разряд (КМС/МС/…), результаты с дисциплиной (algorithmic / product / infosec / robotics / uas), этап, формат, размер команды, место, число участников, подпись. ФСП сможет взять его за основу реальной интеграции (ТЗ: «наиболее удачные решения будут учтены»).
- **ФСП это бонус, а не вход и не оценка**: Profile Strength = 0.85 × (0.75 × процентиль θ в лиге + 0.15 × активность + 0.10 × свежесть) + **FSP Boost (0–15)**. Boost = 12·(1 − e^(−R/2)) + бонус за разряд (1-й +1, КМС +2, МС +3), весами призёр 0.7, победитель 1.0, финалист 0.4, участник 0.15 с потолком; убывающая отдача, идемпотентность. **FSP-достижения никогда не повышают грейд** (тест `test_grade_immutability`). Сильный разработчик без ФСП выше слабого призёра (паритет 0.846).
- **Нет истории ФСП**: нейтральный бейдж «Подтверждено квалификацией платформы», boost = 0, полная функциональность; доп. источник доказательств: регулярные микро-задачи. Сбой реестра: последний снимок + «синхронизация ожидается», онбординг не блокируется. Чужой ФСП ID: 409 `fsp_id_already_linked`.

### 5.5 Использование ИИ и ML (преимущество по ТЗ). Подай как «ИИ там, где он безопасен, и детерминизм там, где он нужен»
| Где | Что | Почему так |
|---|---|---|
| Разбор резюме PDF | LLM-шлюз (GigaChat, отечественная модель) + rule-based запасной вариант; PDF → стек, грейд, стаж, роли, soft skills, предзаполнение профиля | ТЗ требует автораспознавание. Отказоустойчиво: любой сбой = `source: "rules"` с причиной, пользователь видит, что вернул LLM, а что правила |
| Разбор вакансий (JD) | LLM + правила → структура + блюпринт теста | Работодателю не нужно заполнять форму |
| **Защита ПДн (152-ФЗ)** | Локальная маскировка ФИО, email, телефона, ссылок **до** вызова LLM; `assert_clean()` проверяет остаток, иначе вызов блокируется. Red-team: ~120 adversarial-кейсов (обфускация, юникод, омоглифы, переносы) | Данные не покидают контур в открытом виде; домашние LLM |
| Таксономия навыков | 105 навыков, алиасы, опечатки («Postgress», «k8s»), 160 «грязных» кейсов, 100 %, 0 ложных срабатываний | Профили и вакансии на одном языке |
| SemanticFit | эмбеддинги USER-bge-m3 на CPU (deepvk, русский), pgvector HNSW | Смысловая близость описания потребности и опыта; явные режимы off/local/hash без молчаливой подмены |
| «Почему этот кандидат» | LLM только **перефразирует** факты, уже посчитанные скорером; проверка «заземления» (никаких новых чисел и навыков, ≤ 2 предложений), иначе шаблон | Объяснение не может соврать |
| Психометрика/ML-ядро | IRT 3PL, CAT, байесовская оценка, калибровка семейств, монитор дрейфа, Monte Carlo валидация | **Собственные модели, а не вызов чужого API** |
| Оценка, грейд, ранжирование | **Нет LLM** | Объективность и воспроизводимость |

Ключевая фраза слайда: **«LLM пишет текст. Числа считает математика.»** Показать явную границу: слева зелёная зона «где ИИ помогает», справа фиолетовая «где ИИ запрещён: оценка, грейд, ранг».

### 5.6 Техническая проработка и безопасность (7 % + 6 %)

- Документация API: **OpenAPI/Swagger** (`/api/docs`), единый формат ошибок **RFC 7807 problem+json** с каталогом кодов (13 ключевых).

Агент `invariant-auditor` проверяет 7 бизнес-инвариантов перед каждым мёржем. [ОБНОВИТЬ перед печатью: актуальное число из `pytest --collect-only -q`]
- Безопасность: RBAC + проверка владения, Argon2, HttpOnly/SameSite-куки, CSRF, rate limits, журнал аудита контактов, раздельные версионированные согласия (обработка / публикация / синхронизация с ФСП), отзыв согласия скрывает профиль мгновенно.
- Открытый исходный код, без обфускации. [ЗАПОЛНИТЬ: лицензия]
- «Карточка игрока»: стандартизированный **PDF-профиль** (WeasyPrint) с QR-кодом верификации (`/verify/{public_id}`) и водяным знаком компании. Требование ТЗ про автогенерацию PDF.
