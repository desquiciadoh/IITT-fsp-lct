Assessments, Grading, and VacanciesThe initial assessment is configured per category/domain, not per specific vacancy. This test is the sole mechanism that establishes the candidate's verified grade visible to employers."Industry" in the specification refers to an IT domain or discipline (Backend, Frontend, ML, Data Analytics) rather than a business sector like FinTech or Retail. Teams are free to extend specialization taxonomies. Supporting multiple concurrent specializations per candidate is not required for the MVP.Vacancy-specific tasks are an optional modular feature. Not all employers will choose to configure them. The baseline paradigm assumes the employer proactively scouts candidates. An employer may issue targeted vacancy-specific assessments directly or publish them openly.Importing vacancies from external platforms is not required and actively discouraged. The goal is not to build a generic web scraper/aggregator. The platform must prioritize direct, organic communication between candidates and employers within its own ecosystem.Grade assignment is driven entirely by assessment results. FSP achievements affect a candidate's ranking within a category, never the grade itself.The base set of seniority grades is up to the team (Intern, Team Lead, and Elite tiers are optional). A sensible minimum taxonomy is required so judges can validate the grading system.The candidate independently selects their target grade. The assessment confirms or rejects this selection. Suggesting a recommended grade based on resumé parsing or FSP records is permitted.If a candidate fails to confirm their selected grade, the recommended approach is to display the profile with an "Unconfirmed" status flag and derank them in search results, rather than hiding the profile entirely (which removes them from active circulation). Hiding unconfirmed profiles is permitted only if accompanied by sound architectural justification.Grade promotions should ideally be governed by a separate, dedicated assessment rather than an automatic progression from Junior to Middle. Custom progression mechanics are permitted if their underlying rationale is clearly defended.Cooldown rules on grade reassessment: candidates must not rapidly shift grades across consecutive days. Failing an assessment and accepting a lower fallback tier should not burn a retake attempt. Retake policies, score cutoffs (e.g., scoring 7/10 retains the current grade, below 7 causes a demotion), and interval thresholds (e.g., once every 1–2 months) are up to the team, provided the logic is documented and justified. Whether retake attempts draw from an identical or dynamic task pool is also the team's decision.Standard employer tasks are written by the employer. If deterministic reference answers exist, automated grading handles evaluation. Open-ended submissions (custom scripts, architectural designs) are evaluated manually by the employer. This component is optional for MVP, but counts as a strong positive.Displaying salaries as gross or net is inconsequential. The critical requirement is that the salary figure is explicitly labeled as either gross or net.3. LLMs, Sandboxing, and Anti-CheatingLLMs are permitted, including for dynamic test question generation. The primary evaluation criteria are uniqueness and low error rates; grading objectivity remains paramount.Organizers prefer domestic (Russian) foundation models to avoid issues surrounding cross-border personal data transfers. A curated list of approved models will be shared separately. Teams are entirely responsible for their own inference infrastructure and API billing.Cloud-based LLM APIs are acceptable for demonstration purposes (e.g., parsing PDF resumés, generating explainability summaries for matching outputs), provided all models, use cases, and justifications are documented. The evaluation environment provides no GPU hardware.A live code-execution sandbox is not mandatory: an adaptive questionnaire accompanied by code comprehension and debugging exercises is sufficient.Task bank resilience and question uniqueness are mandatory to prevent answer-sharing among applicants. Automated proctoring and anti-LLM cheating safeguards are not strictly required for the MVP, but are viewed favorably. Teams are encouraged to outline conceptual architectural blueprints for future implementations.Archived FSP competitive programming problems can serve as supplementary challenge tiers (offering a substantial grade boost), provided there are mitigations against candidates who have previously solved them. The platform must remain accessible to general software engineers, not just competitive programming alumni. Pre-generated, human-vetted synthetic problem sets are fully acceptable.4. FSP Achievements and FSP IDA verified profile consists of authoritative data ingested directly from FSP ID (contest history, placements, sports ranks), distinct from unverified self-reported resumé claims. Manual moderation of candidate credentials is not required; verification is inherent to FSP ID integration.Mock registries can be synthesized using standard sports programming metrics: tournament placements, official athletic titles/ranks, competitive disciplines, and team-based finishes. This scope is sufficient.No public API or sandbox client exists for FSP ID. The system is new, historical competition archives are sparse, and data schemas remain intentionally unstandardized to avoid constraining hackathon solutions—which may inform the eventual real-world schema. A simulated integration bridge backed by synthetic data is sufficient.Direct access to the production Keycloak environment will not be granted. Baseline authentication flows should be mocked. Given that Keycloak implements open protocols with public documentation, orchestrating a live Keycloak service within Docker Compose is not required.FSP ID is conceived as an SSO identity provider across Federation digital assets. Currently, participant credentials consist primarily of email/password pairs; explicit account numbers may not yet exist in the user portal. Simulating FSP ID login is recommended, while traditional email/password registration can run in parallel. Exclusive reliance on third-party authentication is not mandatory, though mocking FSP ID remains the expected path. Organizers noted they might deploy an integration testbed and enforce FSP ID authorization as a mandatory check; an official update will clarify this point.Enforcing achievement obsolescence (weighting recent results higher than older ones) is conceptually valid. For a newly launched platform, however, this is of low operational relevance given the lack of multi-year historical logs. Teams may deprioritize this feature if engineering overhead is prohibitive.Attributing individual contributions within team hackathons cannot be done accurately: FSP ID does not track task distribution during online stages. A more practical metric is event frequency alongside overall placements (e.g., winner/runner-up vs. preliminary participant) to prevent candidates from artificially padding profiles through mere attendance. Disciplines should not be tiered arbitrarily: all recognized competitions carry equal weight, and artificially ranking national championships above hackathons is discouraged.5. Matching, Contact Data, and Target DemographicsThe operational baseline for the "novel recruitment mechanics" criterion includes: automated categorization, explainable matching logic, and targeted invitations. Unorthodox recruitment workflows are not strictly mandatory, but novel matching paradigms that lead to functional communication channels carry significant scoring weight. Evaluators will assess both procedural novelty and algorithmic precision.Upon a candidate accepting an invitation, their contact information is unmasked exclusively for the inviting employer. Implementing contact revocation mechanisms is optional.Integrated platform messaging was not explicitly mandated. Enabling direct communication within the platform improves user experience compared to an external contact handoff, but omitting it will not incur scoring penalties.The target candidate base covers a broad spectrum: from entry-level FSP participants to senior IT professionals. The specific profile of early-adopter employers will be clarified in the official chat.Baseline legal compliance is sufficient, focusing primarily on Federal Law No. 152-FZ (Personal Data Protection). Employment agreements with 15-year-olds are legally restricted to light labor. Processing personal data and executing agreements for minors aged 15–16 requires explicit parental consent. Supporting workflows for minor candidates is optional for MVP.Employer corporate verification may be implemented as an optional trust badge without blocking core platform interactions.6. Validation Data and Acceptance TestingNo official baseline dataset or ground-truth annotations will be provided, allowing teams creative latitude in modeling. Vacancy-candidate pairs and dataset definitions must be assembled by each team, with methodology and outcomes documented.The evaluation jury will independently take assessments to evaluate reproducibility and discriminatory power (the system's ability to clearly differentiate between seniority grades) using their own internal synthetic profile set. Evaluation is performed manually by human domain experts rather than via automated test suites.Teams must define their own validation protocol, document the procedure, and publish the results. There are no minimum requirements regarding sample size or third-party expert review. Synthetic ground-truth datasets generated by the team are sufficient. Recruiting real candidates for validation is not required. The jury will directly test qualification thresholds and pilot flows.If a team provides a hosted deployment, remote testing against the team's infrastructure may occur after the submission deadline.Requiring judges to complete an end-to-end registration flow is not strictly necessary. An expedited 3–5 minute evaluation route is acceptable; however, judges must be able to actively take assessments rather than merely observing a pre-populated demo account. A dedicated demonstration mode is permissible.Hardware parameters for evaluation: a compact virtual server running roughly 32–64 GB RAM and ~8 vCPUs (informally noted as 8–16 vCPUs). No GPU acceleration is available. Minor overages will be assessed on a case-by-case basis. The "reasonable limits" clause in the specifications is intentionally flexible.No functional or architectural revisions are permitted after the submission deadline. Commit timestamps will be audited to verify repository immutability. Restarting an unhealthy container instance is permissible; modifying business logic is prohibited.7.
